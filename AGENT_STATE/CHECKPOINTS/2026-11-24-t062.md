# Checkpoint — 2026-11-24 — T-062 lexical path builtins

## Scope

Added `path_join`, `path_parent`, `path_name`, `path_stem`, `path_extension`,
and `path_is_absolute` to the checker, interpreter, IR, and native C backend.
They are pure lexical POSIX-style helpers: no filesystem access, no
normalization, no `Path` type, and no containment. Extension splitting uses the
final dot only when it is neither the first nor the last byte. `path_join`
discards the base for an absolute child and is not a sandbox.

## Implementation

- `src/checker.rs`: builtin registry plus one- and two-argument `E0301` checks
  for `Str` paths.
- `src/interp.rs`: byte-scanned `path_name_range`, `path_parent`, `path_stem`,
  `path_extension`, and `path_join`; dynamic non-`Str` values produce `R0005`.
- `src/ir.rs`: native type validation; dynamically typed paths fail with
  `E0401`.
- `src/codegen_c.rs`: byte-scanned C helpers and ordered statement-expression
  emission for `path_join`.
- `docs/decisions/ADR-0030-lexical-path-builtins.md`: exhaustive lexical
  contract and limits.

## Limits

No `Path` type, normalization, component collapsing, `..` confinement,
globbing, filesystem resolution, symlink metadata, Windows drive/UNC support, or
multi-argument `path_join`. Extension splitting is purely textual. The helpers
add no privileges and remove none; applications must validate untrusted path
components before passing results to I/O builtins. Windows native support
remains unverified.
