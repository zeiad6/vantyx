## Defect

Native string interpolation rendered a `Unit` expression as `()` without
emitting the expression. The interpreter evaluates every interpolated
expression, so `"{side()}"` printed `s1` and then `()` there, while native
printed only `()` and never called `side`. A multi-expression probe
(`"x{multi1()}y{multi2()}z"`) lost both calls natively.

Reproducer: `/tmp/opencode/p34/unitstr.vtx`, matched against the interpreter
under clang and GCC.

## Fix

`src/codegen_c.rs::display_value` renders `Unit` as
`((void)(value), vantyx_str_from_unit())`. The expression stays in the emitted
C, so calls, nested output, mutation, and runtime errors are observable, while
the rendered value remains `()`. `display_expr` delegates to `display_value`, so
`print` arguments and interpolation share one rule; `print` still passes an
already-evaluated temporary from its two-phase lowering (T-079).

## Tests

- e2e `unit_interpolation_evaluates_expressions` pins the output of a single
  interpolated call and a two-call interpolation.
- native `unit_interpolation_evaluates_expressions` compares both engines.
- `tools/differential_fuzz.py::functions_program` now contains
  `fn note_interp() -> Unit` and `print("a{{note_interp()}}b")`. The template
  uses doubled braces because it is a Python f-string.

## Specification

- §1 states that every interpolated expression is evaluated exactly once in
  source order, even when it renders as a constant; `Unit` renders as `()`.
- §11 documents the native evaluation rule.
